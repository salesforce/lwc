## How this is measured

The **normal** command, one web-test-runner invocation over the entire `test/**`
suite (no sharding, no per-file hacks):

```bash
cd packages/@lwc/integration-wtr
BROWSERS=chromium VAPOR_FULL_SUITE=1 \
  node ./node_modules/.bin/web-test-runner --config configs/vapor.js
```

- `VAPOR_FULL_SUITE=1` runs the entire existing integration suite (`test/**`)
  under the vapor runtime; without it, only the curated `test-vapor/**` runs.
- Branch: `feat/vapor-mode`. Runtime: `@lwc/engine-vapor` + `@lwc/template-compiler-vapor`.
- Synthetic shadow also supported via `VAPOR_SYNTHETIC_SHADOW=1` (loads the
  `@lwc/synthetic-shadow` polyfill).

## Performance Benchmarks (vapor vs vdom)

Run with: `npx vitest bench --run packages/@lwc/engine-vapor/src/__tests__/krausest.bench.ts`
and `.../perf.bench.ts`. Both compare the SAME component rendered by the vapor
fine-grained runtime vs the VDOM (engine-core-style) path, in-process.

### 2026-06-26 (run BQ era, gap 198)

**krausest.bench.ts** (js-framework-benchmark-style operations on a 1,000-row table):

| Operation                               | Winner    | Ratio             |
| --------------------------------------- | --------- | ----------------- |
| swap two rows (mounted 1,000-row table) | **vapor** | **10.10× faster** |
| remove rows one-by-one (100 rows)       | **vapor** | **6.32× faster**  |
| update every 10th row (1,000-row table) | vapor     | 1.07× faster      |

**perf.bench.ts**:

| Operation                                        | Winner    | Ratio            |
| ------------------------------------------------ | --------- | ---------------- |
| update single value among 100 static rows        | **vapor** | **1.42× faster** |
| update 100 rows of dynamic text                  | vdom      | 2.65× faster     |
| realistic mixed update: 100 rows text+class+attr | vdom      | 1.66× faster     |
| update attributes on 100 elements                | vdom      | 1.11× faster     |

**Read:** vapor wins big on TARGETED/surgical updates (swap, remove, single-value
— only the changed node's effect re-runs). vdom currently wins on BULK create and
update-EVERYTHING (per-binding effect + deep-reactive-membrane overhead adds up
when the whole tree changes at once). This is the perf surface to watch while
closing the WTR gap — avoid changes that add per-node/per-access overhead.
**PERF-REGRESSION GUARD: re-run both benches after any change to the reactivity
membrane (reactivity.ts), the render/effect path (renderEffect.ts,
renderInstance), or per-node prop application (dom/prop.ts).**

**Signal protocol + reactivity suites now 26/26 (was 5 passing + a page CRASH).**
Three independent bugs, each found by isolating + probing:

1. **Trusted-set bridge broken.** The natively-served test helpers
   (`helpers/signals.js`) `import { setTrustedSignalSet } from 'lwc'`, which WTR's
   nodeResolve sent to **engine-dom** — the wrong runtime. So the trusted-signal
   set was published to engine-dom while vapor read an empty `globalThis`
   key → `isTrustedSignalValue` was ALWAYS false → the signal subscribe path was
   dead. Fix: `integration-wtr/helpers/lwc-vapor-shim.js` (re-exports engine-dom
   but overrides `setTrustedSignalSet` to write vapor's `__lwcVaporTrustedSignals__`
   global) + a `resolveImport` in `configs/vapor.js` redirecting the bare `lwc`
   specifier (for native helpers only) to that shim. NOTE: redirecting to the FULL
   vapor bundle hangs page load (2nd runtime instance) — the shim must be tiny.
   (Also added `setContextKeys`/`setTrustedContextSet` exports to the vapor facade
   for parity, though the shim path no longer needs them.)
2. **Re-entrant page CRASH.** Once subscriptions activated, a synchronous
   re-render inside the signal's `notify()` (which iterates its subscribers Set)
   tore down + re-collected subscriptions mid-iteration → infinite loop → tab
   crash (this is why run AO DIPPED to 2975: the signal file crashed instead of
   running). Fix: defer the signal-driven re-render to a `queueMicrotask`
   (matching engine-core's async model; coalesced via `signalRerenderScheduled`).
3. **Subscribe/unsubscribe across `lwc:if` + cross-component props.** Vapor is
   fine-grained: toggling an `lwc:if` tears down only that branch's `EffectScope`,
   never running the instance-level signal cleanup. Fix: tie each subscription's
   (idempotent) cleanup to the active scope via `onScopeDispose` AND capture the
   parent's active scope in `createDeferredChild`, re-establishing it
   (`wireWithScope`) around the deferred `wireChildProps` — so a parent's
   `signal={signal}` child-prop subscription attaches to the parent's branch scope
   and is dropped when the branch (and child) tear down.

### Slot forwarding (static)

Static light-DOM slot forwarding now works. A `<slot slot="Y" name="X">` is a
FORWARDING slot: it resolves the current component's content for slot "X" and
re-projects it into the enclosing component's slot "Y".

**Fixes:**

- `controlFlowKind` routes any `<slot>` with a static `slot=` attr through SLOT IR
  → `createSlot` (a literal `<slot>` element would never resolve `$slotset`).
- SLOT IR gains `forwardAs` (the `slot=` value); codegen passes it to `createSlot`.
- `createSlot(name, slotset, fallback, bind, forwardAs)` re-tags its resolved
  content's top-level elements with `slot="forwardAs"` (via `retagSlot`).
- `resolveLightDomSlots` strips `slot=` from content placed into a TERMINAL slot
  (no forwarding), and the slot-type-mismatch check now keys on scoped-vs-standard
  correctly (was wrongly treating every non-bind createSlot as scoped).

Results (isolated, curated 24/24, units 79/79, no regressions): scoped-slot 9→10,
slot-forwarding/index 0→1, slot-forwarding/duplicates 2/2, light-dom 62→63.

**Remaining forwarding (harder):** dynamic forwarding slot names (`<slot
slot={expr}>` — the slot grouping itself becomes dynamic; reactivity tests, 3) and
